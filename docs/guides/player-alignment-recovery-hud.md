# 选手对齐、恢复、局内 HUD 与赛后 MVP

## 开局选手对齐（M12A）

1. 赛前填写双方五名选手的真实游戏 ID；队伍资料库仍保留原始阵容顺序。
2. 启用屏幕输入并在 Auto BP 中选择游戏窗口。选手识别复用这条窗口采集流，与英雄识别并行。
3. 后端启动时预加载随 npm 依赖安装的英文与简体中文 Tesseract 模型。模型在本机常驻，比赛中无需下载模型或请求远程 AI。启动后 `/api/v1/recognition/players` 返回 `ready` 才开始 OCR。
4. 展开“选手 ID 区域校准”。文字区域默认根据 Pick 头像位置推导；按原画面百分比调整 P1–P5 的文字矩形，裁剪预览应只包含游戏 ID。这些矩形随现有 BP 预设保存。
5. 系统从同一帧裁剪十个 ID，批量识别后只在各自队伍五人中求全局最佳一一映射。大小写、全半角、空格和常见数字/字母混淆会参与匹配；还会比较第二名方案，避免相似 ID 抢占同一槽位。
6. 高置信度自动发送映射，双方各确认一次后停止后台扫描。低置信度持续复核，保留现有顺序；可采用建议或用下拉框交换两个槽位。人工调整会关闭自动对齐，避免识别覆盖修正；需要再次自动识别时重新打开开关。

`bluePlayerSlotOrder` / `redPlayerSlotOrder` 表示“屏幕槽位 → 当前阵容索引”。英雄 assignments 继续按屏幕顺序保存；照片、角色、ID、Player BP 限制、有效局历史和赛后报告通过映射读取身份。下一局/重置 BP 清除当前映射，有效局记录保留当局映射；资料库不会被重排。

自定义本地模型可配置 `.env` 中的 `HOK_OCR_MODEL_DIR` 与 `HOK_OCR_LANGUAGES`，目录内放置未压缩的 `<语言>.traineddata`。默认自带 `eng+chi_sim`；其他文字需要对应本地模型。不要把模型文件、真实参赛 ID、照片或运行数据提交到仓库。

`npm run benchmark:players` 用合成英文 ID 测量十区域批量 OCR。容器测试不能代替真实游戏字体、画面缩放、OBS 和导播电脑的约一秒级开局验收。

## Simulator 联动测试

BP Simulator 控制台现在按用途分成 **BP 识别、换英雄同步、选手 ID 排序** 三种测试。采集页仍保持为独立窗口，Control 应选择该采集页而不是 Simulator 控制页。

开启“Control 联动测试”是一个显式安全开关：浏览器无法可靠、跨端口确认 `getDisplayMedia` 当前究竟选中了哪个窗口，因此 Simulator 不会仅凭 Control 的“屏幕识别”状态就擅自改比赛。只有开启这个开关后，“重置进度”才会同时发送 `reset_draft`，选手 ID 测试才会把生成的赛前 10 人名单写入 Control。英雄 Pick、换英雄结果和 P1–P5 顺序**不会直接同步答案**，仍必须由 Control 从 Simulator 画面识别，以免测试失真。

选手 ID 排序测试流程：

1. 选择测试集：默认混合英文+简中，也可单独测试英文/数字/符号、OCR 易混淆字符、简中或日文。
2. 点击“随机 10 个 ID / 准备房间”。开启 Control 联动时，Simulator 先重置 Control Draft，再把这 10 个 ID 按双方各五人同步为赛前 roster；此时 P1–P5 仍是正常 roster 顺序。
3. 采集页显示自定义房间等待页面。点击 START 后，蓝方五人和红方五人**分别在各自队伍内部**随机排序，不会跨队交换；同时开始计时并进入 BP 画面。
4. Control 的 Player Slot Alignment 从 BP 画面 OCR ID 并更新 `bluePlayerSlotOrder` / `redPlayerSlotOrder`。Simulator 持有随机后的 ground truth，双方顺序完全一致时自动停止计时。
5. 每次随机函数都会避免得到完整 identity 顺序，确保测试真正发生了重排。

默认本地 OCR 仍只保证 `eng+chi_sim`。日文假名测试页已提供，但应在 `HOK_OCR_MODEL_DIR` / `HOK_OCR_LANGUAGES` 配置 `jpn` traineddata 后再作为正式通过项；默认配置下它属于故障/扩展能力压力测试。

换英雄模式会在交换 Simulator 的两个 Pick 槽后开始计时；它不会直接调用 `set_lineup_assignments`。只有 Control 已完成 BP、正在采集 Simulator 且现有 LineupAssignments 识别到变化后，Control assignments 与 Simulator ground truth 一致，计时才结束。这样测到的是实际识别链路耗时。

## 备份与恢复（M15）

后端每分钟检查数据变化，变更后备份；Control 的“备份与恢复”可查看状态、立即备份、导出比赛。最近 20 份完整备份位于数据目录的 `backups/`，覆盖比赛状态、队伍资料库、访问设置与上传媒体（选手照片及赛后字段证据）。完整备份包含私有访问凭据，保存权限为本机私有；比赛导出不包含 `access.json`。

在 `vite-project` 目录运行：

```bash
npm run recovery -- backup
npm run recovery -- verify data/backups/backup-xxx.json
npm run recovery -- export match-export.json
```

恢复/导入前停止后端，再运行：

```bash
npm run recovery -- restore data/backups/backup-xxx.json
npm run recovery -- import match-export.json
npm run server
```

`.env` 中的 `DATA_FILE` / `UPLOAD_DIR` 同样适用于这些命令。`verify` 检查版本、路径、大小与 SHA-256；实际 restore/import 还会在临时目录加载并验证保存的状态与资料库。运行中的后端锁会阻止恢复，避免磁盘状态与内存状态相互覆盖。文件替换失败时回滚已替换的文件。

比赛导入保留接收机器的访问凭据；完整备份恢复会恢复原凭据，旧分享链接也会重新生效。导入仅替换归档中的文件，不删除接收机器上的无关媒体。启动、停止、操作拒绝和备份失败记录于 `logs/operations.jsonl`，日志限制约 1 MiB 并保留一份旧文件，不记录请求内容、口令或 OCR 文本。

## 局内 HUD（M19 第一阶段）

OBS 添加浏览器源 `/overlay/game-hud`，尺寸 1920×1080；使用与 BP Overlay 相同的访问方式。正常背景透明。

Control 展开“局内 HUD / 人头、推塔与资源”：维护双方人头与推塔，添加最多六种中立资源的名称、图标与计数，选择简约或完整密度。队名、Logo、系列赛比分、当前局数、BO 和赛事阶段读取比赛状态；局内统计独立保存，不会修改系列赛大比分。顶部撤销可回退误操作，刷新/重连会恢复服务器状态。

进入下一局或重置 BP 会将局内计数归零，保留资源类型与密度。当前阶段没有自动读取游戏内 HUD；后续自动候选、冻结与字段级回退仍待实机识别方案。

## 赛后报告与 MVP（M20 基础采集链路）

1. 完成换英雄/身份确认并提交有效局，展开“赛后数据与 MVP”，准备本局十人报告。身份、照片、角色、英雄、局数在此时从有效局快照固定，下一局和临时替补不会修改旧报告。
2. 保持游戏结算界面打开，复用 Auto BP 的窗口采集。手动选择总览/生存/输出/团队页及所需字段。
3. 为当前页面、字段的十名选手分别校准数字区域；**按列出的选手身份对齐区域**。不同结算页可能换列、排序，默认矩形只是校准起点，不能直接信任其行顺序。
4. 点击“捕获当前页字段”。一次处理十个数字小区域，返回草稿候选、置信度和原始裁剪证据。检查后应用。OCR 值不会直接覆盖已经人工确认的字段。
5. 数字输入框失焦后保存人工修正，记为人工确认。各页字段合并到同一份报告，百分比范围和整数项由服务端校验。
6. 投票决定 MVP 后，在下拉框选择相应选手；`/overlay/mvp` 立即展示统一蓝/红模板。未选择时页面透明，可清空选择隐藏卡片。

卡片展示 ID、照片、队伍、英雄、K/D/A、评分和本局赛事信息；根据角色选择最多三个可靠亮点。亮点只是展示顺序，程序不会判断 MVP。OCR 置信度低于 85% 的字段不进入自动亮点或主要统计展示，人工确认字段除外；缺失字段显示“—”，其余可靠字段仍可展示。

当前已实现手动指定页与字段、批量本地 OCR、证据保存、草稿合并、人工修正、选择 MVP 和展示。自动判定页面类型/稳定画面、自动跨页面一致性校验、全队数据页及真实结算画面验收仍未完成。
